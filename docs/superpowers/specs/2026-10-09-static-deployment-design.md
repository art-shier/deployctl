# 静态文件部署：统一项目命令

状态：用户于 2026-10-09 确认继续，进入实现计划阶段；产品代码尚未实现。基于 main 21bdf46、CLI 1.12.1。

## 目标与已确认约定

用户希望把构建后的静态文件打成压缩包并上传，部署时下载压缩包并将文件放到指定目录。用户进一步明确：项目资料已经记录部署类型，Docker 和静态项目应使用相同的操作命令，由工具自动分流。

命令中的项目名标识操作对象，不表示部署类型。不增加 `ctl static install`、`ctl docker install`，也不要求安装时再声明类型。支持现有项目组、权限、发布版本、环境目标版本及部署记录。

```bash
ctl publish project-a --version v1.0.0 --package project-a.zip --channel stable
ctl install project-a --prod
ctl upgrade project-a --prod
ctl rollback project-a --prod
ctl status project-a --prod
ctl logs project-a --prod
```

以上是拟实现后的静态项目用法。Docker 命令和标准发布包继续兼容。项目名称仍须显式指定；本次不新增当前项目上下文或省略项目名的隐式定位规则。

## 目录策略的审阅假设

本方案采用**项目独占目标目录、升级完整替换**。共享目录的增量覆盖会保留旧文件，且回滚需要定义逐文件所有权，本期不将两种语义混用。

可选实现是逐文件覆盖，操作较简单，但可能留下旧文件，失败期间可能混合两个版本。推荐版本目录加原子切换，先准备完整文件再切换，保留旧版本供回滚。

## 项目类型

项目新增 `deployment_type`，取值 `docker` 或 `static`。旧数据缺失时按 `docker` 解释；新建项目默认 Docker，在管理台和项目创建 API/CLI 中可选择静态。

类型创建后不可在普通项目更新中改变，避免相同项目/环境把已安装容器误当作文件目录。旧项目的镜像绑定、版本、配置、授权和审计保持原含义。

静态项目无需镜像仓库，`image_repository` 为空；Docker 项目继续执行原镜像仓库验证、仓库锁及 publisher 标准托管路径限制。注册、发布、解析和修改都校验真实项目类型，不能靠请求中的类型字段绕过项目权限。

项目和版本列表显示类型。静态项目详情显示压缩包格式/大小/摘要，隐藏镜像仓库与镜像验证表单。Docker 项目的字段和上传指南保持现有行为。

## 静态产物与发布

静态项目直接接受 ZIP 或 tar.gz，无需 Docker release.yaml、compose.yaml 或镜像 digest。包内相对路径原样保留；部署目录作为归档根目录，工具不猜测并自动剥离 dist/build 等顶层目录。

上传仍调用 `POST /api/v1/projects/{slug}/releases`，使用 version、sha256、可选 channel=stable 和 package。支持可选 source commit；CLI publish 的 `--commit` 为静态包提供来源记录，Docker 包若同时提供此值，必须与原 manifest 一致。同项目、同版本不可用不同类型/格式/摘要/来源覆盖；相同产物重试沿用原记录。

服务端从已授权项目确定验证器，实际识别归档格式，不信任文件后缀或 MIME。静态验证不连接 Registry，不消费镜像验证 Token。上传结束后的发布事务继续在锁定的当前项目归属下再次授权；失败不落正式制品、不推进 stable。

版本元数据保存 deployment_type、archive_format、原始包 SHA256、压缩大小、展开总大小、文件数量及可选 commit。Docker 旧版本缺失这些新增字段时按原格式处理。制品使用原始上传字节，按摘要和格式保存；下载使用实际 Content-Type、长度与同源授权路径。

## 归档校验与资源边界

静态包默认限制：压缩大小 256 MiB，展开文件内容合计 1 GiB，单文件 256 MiB，最多 50,000 个文件/目录条目，路径 UTF-8 最多 4096 字节。Docker 包继续使用现有 10 MiB/5 MiB/1 MiB 等限制，不因静态支持放宽。

服务端和 CLI 共用对应规则的测试夹具。拒绝空包、无普通文件的包、绝对路径、父目录穿越、盘符/反斜杠、重复或规范化重名、文件与目录前缀冲突、符号链接、硬链接、设备、FIFO、加密 ZIP、损坏归档及超出限制的压缩膨胀。允许普通目录与普通文件；归档内脚本仅作为文件，不执行。

上传、下载、校验和解压采用有界流及临时文件，不将大包/完整展开内容同时载入内存。上传的正文上限包含有限 multipart 开销，读取字段仍保持小尺寸限制。临时包由当前操作负责清理；完整校验通过后才登记或切换。

静态文件部署面向 Linux；本地压缩包生成/上传仍可在 Windows 使用。文件权限统一为普通文件 0644、目录 0755，不继承归档的执行位、特殊权限和所有者。

## 统一解析与 CLI 分发

托管 install/upgrade 继续按项目、环境和可选版本调用 resolve。Docker 返回兼容的现有协议；静态响应带类型/格式/文件统计，并声明新的最低 CLI 版本。拟定功能版本为 CLI 1.13.0，实施前如主干已有更高版本，统一选择下一实际版本；设计中的版本号不表示已经发布。

CLI 先检查最低版本和项目类型，下载并校验同源制品，再调用对应的 Docker Manager 或 Static Manager。静态路径不调用 docker info、Compose、镜像拉取或 registry_config。统一的下载进度、退出码、环境选择、--quiet 和结果上报继续适用。

本期静态入口是已注册项目的托管部署，类型来自管理服务。原 Docker 显式 --release 及离线运维保持兼容；不通过 ZIP 文件名猜测项目类型，也不要求用户附加安装类型参数。

静态项目支持 publish/install/upgrade/rollback/status/logs。静态 logs 表示部署事件和失败诊断，界面明确其含义。静态文件没有由 ctl 管理的服务进程；stop/restart 返回适用范围说明，不删除目标文件或暗中重启共享 Nginx/Caddy。

## 目标目录配置

项目环境的 deployment_defaults 增加 target_dir，在管理台静态配置页和 project-config 中维护。组配置可提供 target_dir 默认值，项目同名值覆盖组值。Docker resolve 不返回这个静态字段；静态 resolve 仅返回适用的目录默认值。

命令默认采用项目环境配置。可选 --target-dir 作为没有远端目标目录时的首次安装补充；已有有效远端值保持现有平台配置优先规则。最终目录必须明确，缺失时拒绝安装并提示设置位置，不选当前工作目录作为默认。

目录写入本机部署状态，upgrade/rollback 沿用已有纳管目录。如果远端设置或 CLI 参数要求改变已安装位置，返回明确的迁移提示，本期不自动迁移或遗留第二份公开目录。

仅接受单行有效 UTF-8 的 Linux 绝对路径，不接受根目录、相对路径、控制字符、空路径或指向其他项目部署/配置/缓存的路径。目标父路径不得通过未知链接跳转；目标自身仅允许本工具已登记并校验的切换链接。

第一次安装允许目标不存在或为空目录；现有非空目录、未知链接或其他项目/环境已占用的目录拒绝自动接管。此时不覆盖、不删除原文件，报告冲突供用户安排迁移。目标路径的独立锁和私有所有权记录防止不同项目/环境并发抢占同一目录。

## 静态部署事务

静态部署状态与容器状态分开验证，以 deployment_type 分发；Docker 旧状态无类型标记时仍按原逻辑读取。静态引用绑定版本、归档摘要、经过校验的展开树摘要与目标目录。

流程：解析固定版本 → 下载/校验包 → 获取项目与目标目录锁 → 验证目标所有权 → 解压到新的私有准备区 → 生成并验证文件清单 → 写 pending → 完成版本目录 → 原子替换目标链接 → 验证当前指向 → 提交 current/previous → 上报结果。

已展开内容保留在受管理版本目录的 files 子目录；公开目标仅指向该子目录。原始压缩包、状态、摘要清单、部署诊断和管理来源记录位于公开目录之外，不把平台 Token 或服务器秘密配置复制到静态文件。

准备失败不切换目录。切换后失败恢复原链接和引用，退出非零；首次安装失败移除本次创建的已验证链接。恢复失败或进程中断保留 pending，后续 upgrade 被阻止，可通过统一 rollback 恢复或清理首次候选。

同版本同摘要重试不丢失 previous；不同内容不得覆盖版本。rollback 使用本机校验过的旧文件树和目标绑定，不重新下载最新版本或重新读取远端默认值。用户篡改缓存、清单或链接时拒绝将其作为正常成功状态。

原子切换保证新打开文件看到完整新版本；已经打开旧文件的消费者可继续使用旧文件，不承诺撤销外部进程的文件句柄。Nginx/Caddy、域名、TLS 和访问日志由原有服务器入口管理。

## 配置与钩子的范围

本期静态产物是已经构建完的文件。构建参数进入项目构建脚本；下载后不在部署主机再次构建。静态归档不允许自带安装脚本触发执行。

静态项目环境页提供目标目录和目标版本，不新增浏览器运行变量注入。静态 resolve 不返回 Docker 专用的 runtime_env/install_params 或继承秘密；组内 Docker 变量不会进入静态公开目录。对静态 install/upgrade 提供 --env-var、--set、--unset-env 或 --port/--bind 时明确拒绝适用性错误，不静默忽略。

现有 Docker 的 JSON 配置、pre/post hooks、refresh_config、组配置继承及恢复行为不变。静态运行时配置与钩子如后续需要，单独定义其公开文件、秘密和可变产物边界。

## 构建与项目接入

新增可复用 build-static-release.yml：检出业务与平台的固定引用，验证授权项目类型，执行项目提供的测试/构建命令，对指定产物目录进行有界且确定性的归档，使用 publisher 凭据调用同一 ctl publish。不执行 Docker 构建和 Registry 登录。

工作流只归档产物目录中的内容，保留相对路径，拒绝链接。固定文件顺序、权限、时间戳和压缩头，避免同一构建结果因包装时间变化而冲突。重试可按项目/版本/来源 commit 取得已经登记的相同原始产物。

项目自行选择真实构建命令及产物目录。提供调用模板和静态示例；Docker build-release.yml 及现有 init 用法保持兼容。skill 路由到静态部署说明，强调项目类型来自平台、统一命令和明确目标目录。
